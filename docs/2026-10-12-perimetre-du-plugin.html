1 · Ce que vit quelqu'un qui installe

Affirmation : une commande (ou deux), puis rien d'autre à faire tant qu'il n'a pas besoin d'un service système. Le démon démarre à la première écriture d'un document.

2 · Ce que contient le dépôt

Affirmation : le plugin docpin est la racine du dépôt, parce qu'un plugin ne voit que les fichiers de son dossier et que le code Python y est déjà. La forme visuelle vit dans un sous-dossier.
.claude-plugin/marketplace.jsondeux entrées : docpin (source ./) et la forme visuelle
.claude-plugin/plugin.jsonmanifeste de docpin ; sa version égale celle du paquet, par test
hooks/hooks.jsonbranche l'enregistreur sur Write|Edit, par ${CLAUDE_PLUGIN_ROOT}
hooks/register-on-write.pyl'enregistreur actuel, inchangé sur le fond

plugins/visual-first/hooks/…le contrôleur de documents, qui demande à docpin ce qu'est un document
tests/ · tools/ · docs/copiés avec le plugin, sans effet : rien ne les charge
Pourquoi la racine, et pas plugins/docpin/

Claude Code copie le dossier d'un plugin dans son cache ; un fichier hors de ce dossier n'existe pas pour lui. Mettre docpin dans plugins/docpin/ obligerait à y déplacer src/, donc à changer le pyproject.toml, la CI et tous les chemins du CLAUDE.md. La racine coûte seulement de copier tests/ et docs/ en plus, quelques centaines de Ko.

La documentation officielle (page plugins/publish) décrit justement une entrée dont la source est "./". Qu'un plugin racine puisse contenir le dossier d'un autre plugin de la même marketplace est lu, pas essayé : c'est la mesure 4 du lot 0.

3 · Le démon ne tourne jamais depuis le dossier d'une version

Affirmation : à chaque mise à jour, Claude Code installe le plugin dans un nouveau dossier et supprime l'ancien 14 jours plus tard. Le démon tourne donc depuis une copie stable, dans le dossier de données de docpin, à côté de tes notes.

Pourquoi pas le dossier de données du plugin. Prévu ainsi, changé à la mesure : les variables CLAUDE_PLUGIN_* n'arrivent pas aux commandes de l'outil Bash, d'où la session appelle annotate. Et désinstaller un plugin efface son dossier de données : tes notes n'ont pas à partir avec lui. Tout reste sous ~/.local/share/annotate ; ton registre a continué tel quel.

Le démarrage à la demande (décision Q5) : bin/annotate interroge le port ; si rien ne répond, il lance le démon en arrière-plan (par systemd si l'unité existe) ; si un démon répond, il s'en sert, et s'il tourne une version plus ancienne, la page propose « Restart daemon ». Le service systemd reste disponible par annotate service, et il pointe sur la copie stable.

Aucune dépendance ajoutée : la copie est un shutil.copytree de src/annotate, lancé avec le python3 du système (≥ 3.12, vérifié au démarrage avec un message clair s'il manque).

Décidé ici, motif écrit : ta boucle de développement

Le plugin installé (A1) sert tes sessions, pas ton clone. Pour essayer une modification avant de la publier : claude --plugin-dir ~/workspace/misc/annotate-workflow. Mesuré : il remplace le plugin installé pour cette session, sans doubler ses hooks. Ton démon systemd, lui, continue de tourner le code du clone : il ne bascule pas d'une copie à l'autre à chaque session de développement.
